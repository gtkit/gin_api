# 代码审查清单

提交前逐项自审。不通过则修复，不适用标注 N/A。

**审查一律从代码本身出发，不锚在改动意图上。** 自查失效的根因通常就是这个锚：
只验证「我想改的那件事成了」，不排查「我碰过的面还对不对」。
刚宣布「做完了」的代码，最需要重新当作嫌疑对象。

## 0. 四条强制检查

这四条独立于下面的分类清单，每次审查都要走完：

- [ ] **枚举输入域**：碰过的每个函数，逐个入参枚举边界值——空字符串、元字符
      （glob / 正则 / SQL / 路径）、nil 与 typed-nil、零值、负值、极大值、重复值。
      问「这个参数的全部合法取值里，哪些会让当前实现出错」，
      而不是「我传的那个值能跑通吗」。
- [ ] **新失败模式回审调用方**：每引入一个新的失败模式（部分成功、新错误路径、新超时、
      新并发交错），grep 出该函数的全部调用方，逐个确认其错误处理是按**新世界**写的。
      旧调用方的错误分支通常是按「全成功或全失败」写的。
- [ ] **契约声明必须有反证测试**：任何契约声明（幂等、有界、线程安全、原子、不阻塞、
      最多一次）都必须配一个「若该声明为假就会失败」的测试，否则不许写进文档或注释。
- [ ] **上一轮改过的代码列为最高嫌疑**，不是最低。要重读整个函数与其调用链，
      而不是只看新增的那几行。

## 1. 正确性

- [ ] 业务逻辑覆盖所有分支和边界条件
- [ ] 并发场景无 data race
- [ ] 错误路径都有合理处理和返回
- [ ] nil 检查充分
- [ ] 类型断言用 comma-ok

## 2. 安全性

- [ ] 用户输入已校验、限制长度
- [ ] SQL 参数化，动态字段名有白名单
- [ ] 敏感信息从配置/环境变量/密钥管理获取，不硬编码
- [ ] 业务路由挂了正确的认证/授权中间件——**这条必须人工确认**，
      写在中间件覆盖不到的位置就是公开接口，而编译与测试都不会报错
- [ ] 日志不打印密码、token、完整请求体、密钥
- [ ] **安全类判定 fail-closed**：无法完成校验时拒绝而非放行

## 3. 性能

- [ ] 无 N+1、循环内无不必要查库
- [ ] 列表查询有 LIMIT
- [ ] 大批量操作分批
- [ ] 外部调用有 timeout
- [ ] goroutine 有退出机制
- [ ] 指标标签低基数，无请求方可控的值

## 4. 架构

- [ ] application 没有 import Gin / GORM / repository
- [ ] transport/http 没有 import GORM / repository
- [ ] repository 没有 import Gin / module
- [ ] worker 没有直接 import GORM / repository
- [ ] internal/pkg 没有反向依赖 module
- [ ] 根 `pkg/` 没有 import 本仓 internal、没有直接写日志
- [ ] DTO / application / models 没有 import 基础设施型 paginator
- [ ] runtime 只做装配、options、adapter，不承载业务规则

## 5. 可维护性

- [ ] 命名清晰
- [ ] 错误消息包含上下文，用 `%w` 包装
- [ ] 新增抽象有真实收益
- [ ] 没有无主 TODO / FIXME
- [ ] 优先复用已有 helper / service / repository / middleware
- [ ] **抽取公共函数时，逐个核对被合并的常量与分支为什么不同**——
      两个调用点的参数取值不同通常有原因，统一成一个值就是引入回归

## 6. 测试

- [ ] 核心业务逻辑有单元测试
- [ ] 覆盖 success + error + edge
- [ ] 多组输入用 table-driven（单一场景不强求）
- [ ] mock 经接口注入
- [ ] 断言具体，优先 `errors.Is`/`As`
- [ ] 新增公开行为有对应测试，未扩大测试债务

## 7. 数据一致性

- [ ] 跨表/跨 repo 操作有事务边界
- [ ] 缓存与 DB 有一致性策略
- [ ] 并发写入有 CAS / 锁 / 唯一键保护
- [ ] outbox / 异步副作用在事务提交**之后**执行

## 8. 稳定性与可观测性

- [ ] panic 有 recovery
- [ ] 外部依赖失败有降级或清晰错误
- [ ] 有 request id / task id / trace 线索
- [ ] 关键失败路径有日志或指标
- [ ] 支持优雅关闭，资源在关停路径上被释放

## 9. 资源与泄漏

- [ ] `resp.Body` / 事务 / 文件句柄 / goroutine 正确关闭
- [ ] `Cleanup` 类方法幂等
- [ ] 定时器、ticker 有 `defer Stop()`

## 10. 兼容性与迁移

- [ ] API / DTO / 配置变更有兼容策略
- [ ] migration 有回滚或等价方案
- [ ] 文档和测试同步更新
- [ ] 破坏性变更是 fail-closed 形态（显式报错并指引出路），不静默改语义

## 11. 租户隔离（仅在 `dataisolate.enabled` 为真时适用）

以下两条**无法自动化**，判据只能是人：

- [ ] 受租户约束的数据进缓存时，缓存键含租户维度（键由调用方构造，数据访问层管不到）
- [ ] 新建/修改共享表时，全局唯一索引含判别列（否则两个租户用同一手机号注册会撞唯一键）

它们的共同点是：失效时数据库侧隔离完全正确，问题出在别处，而没有任何 SQL 能看出来。

## 12. 引用真实性

- [ ] 引用的包名、函数名、字段**真实存在**——写之前 `go doc` 或 grep 核实
- [ ] 没有照搬其它项目的 helper / API
- [ ] 文档与注释里的示例代码能编译
- [ ] 不确定处已核实，或明确标注待确认

最后一条不是形式主义：本仓的规范文档曾长期包含三个并不存在的 API
（一个流式库、一个 WebSocket 库、一个 worker 构造函数），照抄的人会在编译时才发现，
而更坏的情况是照抄了一个**存在但被传感器禁止**的调用。
