# 可选能力契约与接入验收

任务队列、上传、出站 HTTP 和审计日志默认未接线。下列内容是派生项目采用能力时应明确的契约；除当前 API 的 OpenAPI 外，不新增业务表、订单、租户系统或生产接线。接线方法见 [可选模块](../internal/optional/README.md)，资源边界见 [容量说明](capacity-and-memory.md)。

## 现有 HTTP 契约

[OpenAPI](openapi.json) 覆盖 `/health`、`/ready` 和 local 模式的四个认证端点。external 模式不注册认证端点。探针使用自身 JSON 结构；业务成功/错误使用 `code/msg/data/request_id` 信封，成功 code=0，空 data 为数组。不能只按 HTTP 200 判业务成功：注册已创建账号但签发失败的现有分支会提示直接登录。

四个认证端点只接受 JSON，正文最多 8192 字节。手机号最长 20，密码最长 72；注册密码至少 8，登录保留旧密码的无最小长度语义；昵称最长 50；refresh_token 最长 512，登出时可省略。长度约束来自 DTO，字节总量来自路由。认证主头为 `Authorization: Bearer <token>`，`App-Token` 兼容存量客户端；同时提供不一致值会被拒绝。令牌及密码不应记录或缓存。

```http
POST /api/v1/auth/login
Content-Type: application/json

{"phone":"13800138000","password":"<your-password>"}
```

```json
{"code":0,"msg":"OK","data":{"access_token":"<access-token>","refresh_token":"<refresh-token>","expires_in":3600,"token_type":"Bearer"},"request_id":"<request-id>"}
```

示例 token 是占位符；expires_in 单位为秒，实际来自有效 JWT 配置。401 表示凭据/令牌无效，403 为账号或权限拒绝，413 为正文超限，415 为类型不支持，422 为绑定/字段校验失败，429 为速率限制，503 为容量/依赖不可用；错误说明可能调整，客户端依赖 code 和状态语义。传输超时/断开不证明服务端副作用未发生。

当前默认路由没有分页接口和日期时间响应字段。已有 `paging.Paging` 使用 currentPage/pageSize/totalPage/totalCount/nextPageURL/prevPageURL；派生接口复用时须声明页码、默认/最大页长和稳定排序，不能擅自另造同义字段。新增日期字段时明确带时区 RFC3339 表示及精度，避免时间戳秒/毫秒混用。字段新增应向后兼容；必填化、改名、缩窄取值、改变状态语义前先给迁移与兼容窗口。

OpenAPI 路由集合通过真实 `bootstrap.buildEngine` 的 local/external 装配双向对照；它防止路径和方法漂移，不证明所有业务语义、权限或真实容量。

## 业务写入幂等

刷新令牌轮换的一次性语义只属于认证，不能当作任意业务写入的幂等方案。需要时由业务定义幂等键的来源、作用域（调用主体和操作）、有效期及同键不同请求的冲突响应。

完整实现应原子保留幂等键与规范化请求摘要，并记录处理中/成功、稳定结果或结果引用。并发首请求只能有一个执行者；同键同请求成功后重放原结果，同键不同请求拒绝；处理中要有明确等待/重试契约和恢复责任。失败、进程重启、响应丢失后的行为由持久状态决定，不能仅靠进程内锁、缓存 TTL 或“看见超时就删除键”。涉及业务事务时，幂等结果提交与业务提交须保持一致。

接入验收覆盖并发相同键、不同摘要冲突、响应丢失后重放、重启、结果过期、处理超时及副作用已发生但记录未完成的恢复。这里不预建表或替业务选择所有这些语义。

## 可选 Outbox / Inbox

需要可靠消息时，在同一数据库事务中写业务状态与待投递事件；提交后由受管投递器发送，持久记录重试、下次尝试和最终处理策略。发布成功与确认写回之间崩溃会导致重复，不能宣称恰好一次。

消费者先以事件 ID/业务版本建立持久化去重或 Inbox，去重状态与业务副作用同事务提交，成功后再确认消息。明确 schema/version、幂等范围、顺序键、超时、最大重试、死信与人工回放权限。不要在业务事务提交前直接发布，再把队列成功当作数据库提交成功。

验收覆盖事务回滚、提交后宕机、发布成功但确认丢失、消费者处理中重投、乱序、毒消息、恢复及可观察的积压/最老年龄/失败数量。

## 多副本定时任务

现有 Scheduler 在每个进程内调度；多副本会分别触发。要求全局调度时，应明确单一调度所有者（外部调度、leader 或具备租约与 fencing 的方案），并在消费端按业务时间窗口实施持久幂等。单一调度者故障切换仍可能重复或漏发，不能省去消费幂等。

明确时区、窗口边界、夏令时、错过窗口补偿、运行上限、部署重启与重叠执行规则。验收覆盖两个副本同时启动、所有者切换、租约过期后旧实例继续运行、滚动退出及同一窗口重复投递。

## 资源归属和可选租户隔离

已有身份校验和角色授权不等于对象级授权。派生业务必须在 application 决定操作权限，并在 repository 查询/更新条件中限定资源归属或可信租户上下文；不能从客户端随意指定的 tenant_id/owner_id 推定权限。

列表、详情、更新、删除、批量、导出与异步任务都要限制相同数据范围。未找到与无权访问的对客行为应遵循业务的防枚举策略。验收包括合法用户访问他人 ID、跨租户批量请求、伪造归属字段、间接引用与权限撤销后的行为；本次不增加租户字段或虚构权限矩阵。

## 审计可靠性

当前可选审计是尽力而为：队列满、落库失败或关停丢弃会累计 Dropped；它不能承诺关键操作的可靠审计。审计不能代替业务事实，也不能写入密码、令牌或敏感正文。

不能丢失的关键操作应采用与业务同事务的审计记录或持久化事件，并定义审计失败是否阻止业务、访问控制、保留期限、防篡改与恢复流程。验收覆盖持久化失败、队列满、断电/重启、落库成功但确认丢失和回放重复，确认数据与审计的提交关系。对不同操作是否允许丢失，由业务明确选择，不能把异步入队成功当作可靠落库。
