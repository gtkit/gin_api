## 二、文件一致性的实施细节（04）

**客户端可见性。** 普通上传和 merge 只有在内容写入完成、校验通过且 files 记录提交后才返回成功。DELETE 首先在同一短事务里锁定属于调用人的行、写删除意图并软删，使新的详情、列表和下载立即看不到该文件；随后尝试物理删除，确认已删除或确实不存在后才返回成功。存储短暂故障返回 503，后台继续重试，客户端此时可能查到 404。相同 owner 重试已登记的删除可取得完成结果；其他 owner 或从未存在的 ID 沿用 404。删除前已打开的下载可能继续完成。

**持久化的最小单位。** 采用一张 file_operations 表，逻辑操作用主行、额外写尝试用带 parent_id 的子行记录；主行对业务键唯一，子行对 parent_id 与尝试代次唯一。业务键不含凭据。新表保存操作 ID、操作种类、owner、逻辑业务键、稳定文件 ID、驱动、桶、实际对象键、文件元数据、预期大小/摘要及算法、处理状态、尝试代次、租约到期、下次执行时间和固定错误类别。普通上传以服务端生成的操作 ID、merge 以 owner + upload_id、删除以 owner + file_id 标识；建立业务唯一约束和按状态/下次执行时间的领取索引。一次可能写入的不同对象键须各自持久可追踪；归属未查清的键绝不重新分配。对外提供的列表仍只查 files。MySQL 只包住准入、认领和最终提交，外部存储 I/O 全在事务外。

| 步骤 | 实施决定 | 故障后如何收敛 |
|---|---|---|
| 认领 | 持久登记 intent 后才允许写最终对象。稳定文件 ID 随操作生成；相同 merge 读到已完成操作就返回相同 ID，遇到未完成工作沿用已有“合并中”契约。用唯一键和条件更新防止多实例都成为提交者。 | 旧代次即使迟到完成也不能覆盖新提交。每个实际写入目标留独立尝试记录；前一尝试结果不明时暂停重新写入，同一物理键不能有两个未决写者。已删除文件对应的 merge 返回不可用，不复活记录。 |
| 普通上传 | SDK v1.8.1 的普通 Upload 在 Save 前才生成随机 key。改由 runtime 适配器从已校验的有界缓冲或临时文件向现有 `Uploader.Storage().Save` 写入预分配、已登记的唯一键。沿用现有文件名规范化、扩展名白名单、实际字节上限、默认 SHA-256、MIME 推断；用现有合法/异常输入和返回字段做兼容对照。 | 写完未提交时，可依据事先登记的长度与摘要，在恢复限速下核验对象并补交。写到一半、无对象或临时文件已丢，终止或隔离本次操作，客户端可重新上传。存储超时不等于没有写入。 |
| 分片合并 | local 保留 SDK 预分配和原子落位，adapter 借用现有 chunk store 的 `GetSession`，在核对 owner 后、调用 merge 前登记该会话的 StorageKey。S3 当前走代理合并，给它接公开 `WithStorageResolver` 的 Save 包装，在放行底层 Save 前以条件更新登记 SDK 当次生成的真实键，登记失败直接终止。仅 S3 接 resolver，保留 local 原生装配优化。新会话在 init 时以相同 TTL 绑定创建时的 driver、bucket 和 owner，与后续 merge 核对；滚动切换应先给旧会话留出旧位置完成的窗口。无位置凭据的旧会话仅在可证明存储未变时接管，否则提示重新初始化。SDK 的完成回调太晚，不作登记入口。 | SDK 返回结果后再提交业务完成状态。SDK 成功但 Redis 会话终态落盘失败时，以相同 owner 的持久操作定局；已完成操作可重放。进程在 SDK 返回前退出时只凭可重建的完整校验链补交；没有可信摘要或等价完成凭据就隔离或要求重新上传。单凭对象存在、大小相同或 S3 ETag 均不足以发布。 |
| 提交、删除与对账 | 同一 DB 事务插入 files 并更新操作为完成；若唯一键已存在，重新核对 owner、文件 ID 与物理位置。删除后台使用持久化目标，核对共享引用和归属后删除；历史共享对象仅在最后有效引用消失且能证明归属时才物理回收。 | 禁止为补偿失败而直接按上传响应中的键删除。超时后保留未知状态，等待写者终止并复查；仅处理本系统可证明独占且无已提交引用的键。重试采用有界批量、退避和抖动，超过重试期限进入人工待核对并告警；正常完成、待重试、最老积压、隔离与恢复耗时均可查询。终态明细按批保留至会话 TTL、客户端重试和人工对账窗口中最长者结束；未决记录不清理。文件软删后保留最小墓碑至少至该会话不可能重放，超过约定保留期的 DELETE 重试按既有 404。 |
| 部署与回退 | 首先执行增量建表并盘点历史桶、重复物理引用、NULL 时间和本地根目录。先部署所有兼容读端及休眠 worker；切换时暂停并排空旧文件写入/合并，确认无旧 writer 后再启用新写流程与 worker。存量完成文件直接读取，历史孤儿先出只读清单。 | 故障时先停止接收新文件写入，保留读端与操作表，待执行中的动作安全结束或交回接管后回退。**已有未决意图时不得恢复旧删除/合并写路径或回滚 DDL**。安全修复版本作回退下限。升级前已完成的分片会话按 SDK 原记录与 owner、存储键关联，已有 files 行直接复用原文件 ID，不能补造第二份。 |

**多副本约束。** 分片会话在 Redis，代理分片内容在 `chunk_dir`，local 最终内容还依赖 `dir`。要求故障转移的部署须让接管副本访问同一份持久数据；SDK 会话过期清理、应用临时文件清理和业务对象对账各管自己的命名空间。使用实例专属临时子目录与存活判定回收进程崩溃的临时文件，不触碰在用分片。仅有会话粘性无法覆盖原实例永久丢失。S3 代理合并在当前 SDK 中会打开全部分片再读取；在 chunk store 的 `OpenChunkData` 适配层做按需打开、读完关闭，保持取消和提前 Close 有效，在真实多分片负载下验证打开文件数有界。跨进程读写、文件原子落位和卷可用性须在所选文件系统实际验证。

## 三、把三个现有模块做成可复制的示例

| 示例 | 标准化后的职责 | 应当直接复用的做法 |
|---|---|---|
| `example` · 带账号归属的 CRUD | 保留 `application/commands.go` 的具名输入、`dto` 的 HTTP 校验和 `runtime/module/example` 的装配。Create、单条软删目前各只有一条写 SQL，去掉外层单语句事务，以真实 MySQL 对比确认往返减少；Update 保留短事务，以带 owner 的当前读锁定目标，等值更新时返回真实记录，避免把 MySQL “值未变化”解释成 404；DeleteMany 保留事务，影响行数少于请求数则回滚全部。 | 展示 1–100 个不同 ID 的批量原子性、更新最后写入生效的现有约定和列表的精确总数。示例路由由派生项目显式注册，默认 server 不公开它。专用 HMAC 回调另行注册，生成普通 CRUD 时不复制。 |
| `auth` · 凭据、身份与会话 | `transport/http` 只解析凭据与受信身份；`application` 明确区分登录、刷新、单次退出、全部退出与改密；`runtime/module/auth` 翻译 Redis/数据库错误、注入哈希并发门和会话端口。复用现有认证与授权中间件。 | 展示如何把故障、无效凭据和限额区分；凭据校验有独立 CPU/排队预算。账号停用、改密、全部退出后，新认证请求必须按主库版本校验；已经完成认证的在途请求采用既有语义。其他业务拿已认证 UID，不自行调用登录接口。 |

### 今后新增 internal/module 的约定

1. **装配与调用。** `bootstrap → runtime/module/<m> → application`。HTTP 和 worker 调 application；repository 接触模型、事务和参数化 SQL。业务 A 需要业务 B 时，先定义 A 真正消费的最小能力，由 runtime 注入 B 已有的应用方法或适配器，传已验证主体、稳定 ID 和 context。默认走进程内同步调用，不增加内部 HTTP、自建连接池、全局服务注册表或双向 import。只有需要异步交付、重试或时间解耦的工作才进入队列。
2. **接口与权限。** 每条路由声明方法、输入、认证来源、操作权限、资源归属、大小/时间上限以及失败响应。路由判断“可否执行该类动作”，数据查询和条件写入判断“对象是否属于此人”。owner 来自认证上下文，列表、详情、更新、删除、批处理、导出、缓存键和幂等键都带归属维度。响应使用显式 DTO 或安全的应用视图；数据库模型和供应商对象不直接作为协议。
3. **事务与幂等。** 唯一性用数据库唯一约束兜底。多行修改和影响行数断言同事务，集合内混入一条无权记录也全部回滚。跨模块且同库的原子用例由发起用例拥有唯一事务边界；跨存储或外部副作用定义持久操作键、未知结果、重试与对账方式。任何自动重试都要说明重复执行的结果。
4. **时延与生命周期。** 请求从入口到 SQL、Redis、RPC/存储透传 context；下游和池等待共享剩余预算。分页有稳定顺序与查询上限，按访问模式配置索引。CPU 密集、长传输和后台恢复分别给并发、等待、内存/临时盘预算；过载使用既定 429/503，取消释放名额。worker 由应用生命周期启动和等待结束，持有者关闭资源一次，借用者不关闭。
5. **契约与观测。** 在模块说明记明路由开关、依赖必需性、错误映射、schema、兼容期、回滚路径及 SLO。指标使用路由模板、操作和结果作为有限标签，owner、文件 ID、token 不作指标标签。跨层用 request ID/trace 关联。只有字段、上限与公开语义一致的逻辑才复用，不为三个示例建万能基类。
6. **生成器也要验收。** 把 `example` 通用 CRUD 的具名输入、owner 条件、事务边界和回归断言同步进 service、handler、repository、runtime 及各自的测试模板；按需调整模板清单。变更的渲染结果在内存中检查 Go 语法、签名、导入方向及路由契约，结合现有实例的真实 SQL/HTTP 回归。渲染器不覆盖已有模块，不把演示路由挂进默认服务。

## 四、如何验收并发、故障恢复和跨账号隔离

使用可控测试数据：A、B 两个独立账号均拥有同一业务权限，A 另有两个设备会话；再设一个已认证但没有动作权限的账号。隔离、权限拒绝和数据不存在分别测试。默认、optional、scaffold 三种构建分别验证；服务以正常装配入口运行，示例模块由测试宿主显式挂载。锁定相同的应用与依赖版本、CPU/内存配额、实例数、数据量和配置。外部或生产环境操作另行授权。

| 编号和场景 | 测试安排 | 通过条件 |
|---|---|---|
| A1 · 账号与会话 | 分别运行本人退出、只带 access、带 B 的 refresh、无效/过期 refresh；并发执行 A 的刷新和同一家族退出。覆盖原令牌、轮换后继、相同账号不同家族、旧版本记录；模拟撤家族成功后撤 JTI 暂时失败。 | A 的动作不能改变 B 的访问或刷新能力；当前 JTI 最终撤销，指定的本人家族在完整退出后无可用刷新后继。其他家族维持原有状态。令牌不匹配时客户端看不到其归属。部分失败可重试；独立已签发 access 和账号级 logout-all 分别按原契约断言。 |
| A2 · 文件、分片与位置 | A、B 上传相同文件名和内容，各自做 list/get/download/delete。用两个桶准备同键不同内容，在位置不匹配时观察 adapter 调用数。覆盖 A、B 的 status/chunk/resume/abort/merge、分页游标和 A/B 并行删除。 | 资源行按 owner 过滤；他人文件与不存在同为既有 404，分片会话权限沿用既有 403/404 区分。B 的进度、内容、文件数和摘要全程正确，resume 不揭示他人会话；错桶存储 Get/Delete 调用均为零。过去合法游标可用，跨账号游标不返回数据。 |
| A3 · CRUD | A、B 各建记录；混合 owner 的批删中把无权项放在首、中、末位置；同一标题重复更新；并发更新/软删、批删/单删。既检查 HTTP status/业务码，也查库。 | 越权与缺失同样响应，整个失败批次影响行数为零；对象无复活，无重复创建，成功的等值更新不会报 404。没有动作权限的账号在触达仓储前被拒绝。 |
| F1 · 依赖与恢复 | 组合 external/local auth、upload/tasks 开关和不同 Redis 限流失败策略。分别验证启动前缺依赖、服务运行后断连、恢复、恢复中关停；tracing 开/关均覆盖。 | 必需性与配置、doctor、readiness 一致；必需失败禁止就绪，允许降级的能力按其既有策略工作。依赖恢复后在预期探针缓存和重试窗口内恢复，健康检查不放大连接数，不遗留恢复协程。 |
| F2 · 文件提交与多实例 | 在“意图提交后”“写对象后/写 files 前”“DB 提交但客户端未收响应”“软删后/物理删前”“物理删后/完成标记前”分别中断测试进程，由另一实例接管；另测存储超时但随后完成、Redis 终态写失败、双 worker、租约过期与旧写者迟到。local、S3 兼容存储各测一轮。 | 每个成功 merge 最多一条业务文件，重复成功得到同一 ID；已返回成功的文件可读且摘要一致。不可验证的对象不可见且有可追踪意图；恢复后已确认删除的对象及无主的可回收对象在约定窗口内收敛。每个待核对项均可定位，绝不删除其他账号、其他桶或现有正常文件。 |
| F3 · 超时、过载与摘流 | HTTP/1.1 连接复用与 HTTP/2 多流分别测：短请求慢读体、大上传、超限/无 Content-Length、中途断连、临时区满、下载写出后中断，及 transfer 满载时普通鉴权读。正常摘流和强制中断各测一次。 | 较短预算生效，前一请求的 deadline 不污染下一请求或同连接其他流。已写响应不会再拼接错误 JSON；配额、FD、临时文件、连接数回落，普通读的 P99 符合约定。进程在终止宽限内退出；跨实例能继续或给出明确可重试结果。 |
| F4 · 队列、审计、恢复卷 | 注册真实测试 handler 后重复投递同一业务键，执行中断、重启后验最终副作用。审计在成功、错误映射、队满、DB 慢与关停场景核对。让第二副本继续第一副本的分片；另测挂载丢失。 | 队列副作用只成功一次；producer-only 配置没有伪造的消费通过证据。审计落库结果、丢弃计数与实际请求吻合，panic 沿用 recovery 路径。文件恢复不依赖 best-effort 审计；挂载不满足容灾要求时明确判该部署不准入。 |
| C1 · 查询与计量 | 同一数据库准备小账号、大账号、同秒记录、历史 NULL 时间和深页。对页码、游标、认证、刷新分别记录 SQL 次数、选列与执行计划，区分 JWT 缓存冷、热。HTTP 耗时用测试 reader 与客户端双计量。 | 游标无 COUNT，每页至多 size+1；在稳定数据集遍历无缺失无重复，并发插入时按既定排序边界读取。刷新不取密码哈希。P99、SQL 扫描行数、主库连接等待与导出 histogram 样本数均有前后对照。 |
| C2 · 混合容量 | 用相同脚本和种子对基线、候选分别预热 5 分钟，从预计峰值的 25%、50%、75%、100% 每档 10 分钟，峰值稳态 30 分钟，再做 150% 的 5 分钟过载与 10 分钟恢复，各重复三轮。使用固定到达率、有限并发/等待，记录未发出或丢弃的请求。请求混合包含鉴权读、登录/刷新、热/深分页、单文件、分片合并/下载。 | 依次报告每条路由的目标/实际到达率、业务成功 RPS、P50/P95/P99、排队、429/503、超时和错误。采集 CPU、RSS/堆、GC、goroutine、FD、临时盘吞吐、DB/Redis 等待及恢复积压。上传按大小分组，报首字节、总耗时和 MiB/s；普通鉴权读单列。不得把快速拒绝、HTTP 200 业务失败或发压机饱和计算为提升。 |
| M1 · 契约与骨架 | 对照旧、新服务的路由清单、HTTP 状态/业务码、JSON 字段及下载头；覆盖已有客户端 DTO、开关组合和旧库/迁移后库。用默认项目和显式模块测试宿主验证，再检查生成器内存渲染结果。 | 合法旧请求和已发会话按约定工作；默认构建不引入可选组件或自动暴露样例。所有刻意变化能对应第一节的一项和一个回归用例。 |

## 五、实施与发布的停靠点

1. **冻结契约。** 在原仓记录旧接口与各开关、旧 Redis 数据、历史 files 行及可复现请求集。补齐上表业务目标。先建立 01–03 的隔离和启动回归用例，再实施该批；验收 A1、A2、F1。
2. **建立可比的基线。** 以客户端延迟为准记录修复前样本；09 单独上线时校准计数。按 05、06 落实传输边界和临时区，验证 F3；在引入 04 的额外 DB 写与恢复工作前保存文件吞吐及磁盘基线。
