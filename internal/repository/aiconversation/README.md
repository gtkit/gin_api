# repository/aiconversation

AI 对话的**聚合仓储**。会话是聚合根，消息是其内部实体。

## 聚合边界

| 项 | 内容 |
|---|---|
| 覆盖表 | `ai_conversations`（聚合根）、`ai_messages`（内部实体） |
| 外部介质 | 无 |
| 事务边界 | `SaveTurn` 在**本仓储内部**开事务：会话（不存在则新建）+ 两条消息 + 会话汇总列，四次写入原子提交 |
| 缓存边界 | 无缓存。上下文每轮查库；加缓存前先想清楚失效点是 `SaveTurn` 还是 `Delete` |

## 为什么不拆成两个一表一 repo

`ai_conversations` 上的 `message_count` / `prompt_tokens` / `completion_tokens` 是消息的冗余汇总，
必须与消息写入原子提交。拆开之后，「同时更新两张表」这条不变量就只能靠调用方每次都记得开事务并按
正确顺序调用两个仓储——漏掉一次不会有任何报错，只会让计数悄悄偏离真值，而计数正是用来对账 token
成本的东西。

冗余本身是为了会话列表：按 `conversation_id` 做 `COUNT`/`SUM` 的成本随对话长度线性增长，
而会话列表是最高频的读。

## 归属校验写在 SQL 里

`GetOwned` / `Rename` / `Delete` 都把 `user_id = ?` 写进 WHERE，而不是取回后由调用方比对。
比对是可以忘的，忘掉的后果是任何人凭猜 ID 就能读到别人的对话。

`GetOwned` 刻意**不区分**「不存在」与「不是你的」：区分开等于提供一条可枚举的存在性信道。

`ListMessages` 是例外，它不做归属校验——调用方必须先经 `GetOwned` 确认。调用点只有一处
（`module/ai/application` 的会话详情编排），由那一处的测试盯住；在这里再查一次等于每次列消息
都多一次往返。

## 删除语义

`Delete` 只软删会话头，**不动消息**。会话软删后任何经 `GetOwned` 的读取都取不到它，消息也就再无
入口；给几百上千条消息逐条打软删标记换不来更强的不可见性，代价却是一次可能很长的事务。

物理清理（含消息行）属于保留期任务的职责：保留期必须由使用方按所在司法辖区决定，
本仓不预设数字。对话正文可能包含用户输入的个人信息，接入前请一并落定清理策略。

## 外部调用不得进事务

`SaveTurn` 只做本地写入，模型调用必须在它**之前**完成。把 LLM 调用包进事务是长事务与连接池
耗尽的典型来源——一次上游卡顿会按住一个数据库连接直到超时。
