`internal/bootstrap/app.go:164`：绑定失败即启动失败，运行期异常退出会被 readiness 标为

## 3. 推荐执行顺序

### 3.1 先做自检

```bash
./pprof/scripts/doctor.sh
```

端点未启用（`pprof.enabled: false`）或服务没在跑时，"端点不可访问"是预期结果，doctor 会报 ⚠ 而不是 ✗。

### 3.2 开启端点

端点已内置，只需在目标环境的配置文件里打开：

```yaml
pprof:
  enabled: true
  host: 127.0.0.1
  port: "6060"
```

启动后验证：

```bash
curl -s http://127.0.0.1:6060/debug/pprof/ | head -20
```

字段语义与安全边界见 `01-pprof性能调优指南.md` 第 3.3 节。

### 3.3 采集第一组基线

服务启动并有代表性流量后执行：

```bash
./pprof/scripts/collect.sh cpu 30
./pprof/scripts/collect.sh heap
./pprof/scripts/collect.sh goroutine
./pprof/scripts/collect.sh goroutineleak   # 泄漏集合；会强制一次 GC，别高频跑
```

分析 CPU：

```bash
./pprof/scripts/analyze.sh pprof/profiles/cpu-<时间戳>.pprof
```

分析 heap：

```bash
./pprof/scripts/analyze.sh pprof/profiles/heap-<时间戳>.pprof
```

### 3.4 做手动调优

按这个闭环执行：

1. 记录基线：QPS、P50/P99、CPU、RSS、GC、goroutine 数；
2. 采 profile；
3. 用火焰图或 `top/list` 定位最宽、最重、最可解释的热点；
4. 一次只改一个热点；
5. 用相同压测参数复测；
6. 用 `go tool pprof -base old new` 对比优化前后；
7. 增加或更新 benchmark，防止回归。

### 3.5 再做 PGO

PGO 建议做，但不要替代手动调优。顺序应是：

1. 先用 pprof 修掉明显热点；
2. 在代表性负载下采集多份 CPU profile；
3. 合并为根目录 `default.pgo`；
4. 验证 `go build` 启用 PGO；
5. 用 benchmark 或端到端压测确认收益。

命令：

```bash
PPROF_ADDR=127.0.0.1:6060 ./pprof/scripts/pgo-merge.sh collect 3 30
./pprof/scripts/pgo-merge.sh merge
./pprof/scripts/pgo-merge.sh verify
```

## 4. 现状说明与后续建议

> 4.1、4.2 是**当前状态**（回答"这块已经怎样了"）；4.3 起是尚未做、可按需推进的建议。

### 4.1 产物与文档的入库边界（当前状态）

- 根 `.gitignore` 里**没有** `*.md` 规则，`pprof/*.md` 正常被跟踪，随仓库分发。
- 采集产物（`profiles/`、`*.pprof`、`*.prof`、`*.pb.gz`、`*.out`）由 `pprof/.gitignore` 忽略。
- PGO 的 `default.pgo` 在项目根目录且**必须提交**，任何 `.gitignore` 都不该忽略它。

### 4.2 端点行为的现有测试

`internal/bootstrap/pprof_test.go` 已覆盖：

- 未启用时不建立任何监听；
- 绑定失败让启动失败，且失败时不开启采样；
- 端点真的可访问，关停后端口可再绑；
- 关停把 block/mutex 采样率清零，且重复关停不阻塞；
- 用独立 mux，不污染 `DefaultServeMux`；
- **`runtime/pprof` 的每个内置 profile 都能在独立 mux 上取到 handler**——
  这条是反证测试：把注册改成手工白名单、漏掉 `goroutineleak`，它就会失败；
- `/debug/pprof/goroutineleak` 真的返回 goroutineleak profile。

### 4.3 增加热点接口压测脚本

当前脚本负责采集与分析，但没有封装业务压测。等你确认“热点接口清单”后，可以补一个项目专用脚本，例如：

```text
pprof/scripts/load-hotpaths.sh
```

它只负责对真实高频接口施压，`collect.sh` 同时采样。不要在没有热点接口清单时提前写死 URL。

### 4.4 形成 baseline 目录

建议保留一份“优化前基线”说明，不提交 profile 大文件，只提交文字指标：

```text
pprof/baselines/
  2026-06-25-dev-hotpaths.md
```

记录：

- 二进制版本 / commit；
- 配置环境；
- 压测命令；
- QPS、P50、P95、P99；
- CPU、RSS、GC、goroutine；
- 对应 profile 文件名。

### 4.5 多实例生产环境再考虑持续 profiling

如果后续生产是多副本部署，建议再评估持续 profiling：

- 定期随机选择一个实例采样；
- 每次只采一种 profile；
- CPU/trace 避开极端高峰；
- block/mutex 只在排查时临时开启；
- profile 产物不要长期放在应用机器上。
