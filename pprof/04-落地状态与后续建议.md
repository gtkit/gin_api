我已经核对过当前源码：`internal/platform/config.Config` 里还没有 `Pprof` 配置字段，`internal/bootstrap` 里也还没有独立 pprof server 生命周期代码。也就是说，当前 `pprof/` 目录提供的是“落地方案 + 操作手册 + 脚本工具箱”，不是“项目已经接入完成”的证明。

所以现在直接跑 `./pprof/scripts/collect.sh cpu`，如果服务没有另外手动暴露 `/debug/pprof/`，会连接失败。要真正开始采样，先按 `01-pprof性能调优指南.md` 第 3 节把 pprof 端点接入项目，再启动服务验证。

## 3. 推荐执行顺序

### 3.1 先做自检

```bash
./pprof/scripts/doctor.sh
```

如果服务还没接入 pprof，端点不可访问是预期结果。

### 3.2 接入 pprof 端点

按 `01-pprof性能调优指南.md` 第 3 节执行：

1. 在 `internal/platform/config/types.go` 增加 `PprofConfig`；
2. 在环境配置文件中增加 `pprof:` 配置；
3. 新增 `internal/bootstrap/pprof.go`；
4. 在 `App.Run` 生命周期里启动和关闭 pprof server；
5. 本地启动 `make dev` 后访问：

```bash
curl -s http://127.0.0.1:6060/debug/pprof/ | head -20
```

### 3.3 采集第一组基线

服务启动并有代表性流量后执行：

```bash
./pprof/scripts/collect.sh cpu 30
./pprof/scripts/collect.sh heap
./pprof/scripts/collect.sh goroutine
```

分析 CPU：

```bash
./pprof/scripts/analyze.sh pprof/profiles/cpu-<时间戳>.pprof
```

分析 heap：

```bash
./pprof/scripts/analyze.sh pprof/profiles/heap-<时间戳>.pprof
```

### 3.4 做手动调优

按这个闭环执行：

1. 记录基线：QPS、P50/P99、CPU、RSS、GC、goroutine 数；
2. 采 profile；
3. 用火焰图或 `top/list` 定位最宽、最重、最可解释的热点；
4. 一次只改一个热点；
5. 用相同压测参数复测；
6. 用 `go tool pprof -base old new` 对比优化前后；
7. 增加或更新 benchmark，防止回归。

### 3.5 再做 PGO

PGO 建议做，但不要替代手动调优。顺序应是：

1. 先用 pprof 修掉明显热点；
2. 在代表性负载下采集多份 CPU profile；
3. 合并为根目录 `default.pgo`；
4. 验证 `go build` 启用 PGO；
5. 用 benchmark 或端到端压测确认收益。

命令：

```bash
PPROF_ADDR=127.0.0.1:6060 ./pprof/scripts/pgo-merge.sh collect 3 30
./pprof/scripts/pgo-merge.sh merge
./pprof/scripts/pgo-merge.sh verify
```

## 4. 还推荐补什么

### 4.1 明确是否要提交文档

根 `.gitignore` 当前是：

```gitignore
#*.md
```

所以 `pprof/*.md` 目前可以被 Git 跟踪。若以后恢复启用 `*.md`，需要在根 `.gitignore` 的 `*.md` 规则之后加入：

```gitignore
!pprof/**/*.md
```

只有在重新启用 `*.md` 时才需要这个例外。

### 4.2 接入代码后补测试

如果后续真的把 pprof server 接入 `internal/bootstrap`，建议至少补这些测试：

- `PprofConfig` 默认值和配置解析；
- `startPprofServer` 在 `Enabled=false` 时不监听；
- 监听地址默认只使用 `127.0.0.1:6060`；
- `block_profile_rate` / `mutex_profile_fraction` 只在显式配置时开启。

### 4.3 增加热点接口压测脚本

当前脚本负责采集与分析，但没有封装业务压测。等你确认“热点接口清单”后，可以补一个项目专用脚本，例如：

```text
pprof/scripts/load-hotpaths.sh
```

它只负责对真实高频接口施压，`collect.sh` 同时采样。不要在没有热点接口清单时提前写死 URL。

### 4.4 形成 baseline 目录

建议保留一份“优化前基线”说明，不提交 profile 大文件，只提交文字指标：

```text
pprof/baselines/
  2026-06-25-dev-hotpaths.md
```

记录：

- 二进制版本 / commit；
- 配置环境；
- 压测命令；
- QPS、P50、P95、P99；
- CPU、RSS、GC、goroutine；
- 对应 profile 文件名。

### 4.5 多实例生产环境再考虑持续 profiling

如果后续生产是多副本部署，建议再评估持续 profiling：

- 定期随机选择一个实例采样；
- 每次只采一种 profile；
- CPU/trace 避开极端高峰；
- block/mutex 只在排查时临时开启；
- profile 产物不要长期放在应用机器上。
